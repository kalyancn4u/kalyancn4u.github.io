1. GROUND RULES (read before doing any work)
--------------------------------------------------------------------------------
1.1  OUTPUT IS ALWAYS THE LIGHT THEME, and DARK FILES ARE ENTIRELY OUT OF SCOPE.
     Every dark-theme file (git_cheatsheet_dark, scipy_cheatsheet_dark,
     xgboost_cheatsheet_dark, the postgres_master_reference_dark_* set) is LEFT EXACTLY
     AS-IS: do NOT edit it, and do NOT mine it for content. (Superseded earlier guidance
     that said to fold dark content into the light file — we no longer do that.)
1.2  ONE FILE PER TOPIC — MODIFY ONLY THE LATEST VERSION. For each topic, the ONLY file
     that may be modified / extended / updated is its CURRENT LATEST version. Everything
     else is left exactly as-is and never touched: all older versions, "(1)" duplicates,
     AND all dark-theme files. Always confirm the file you are about to change is the
     latest by resolving it in the CURRENT FILE MAP (section 4). If unsure, re-derive the
     latest from disk (highest _vN; no-suffix = v0) BEFORE editing.
     Reconciliation with rule 1.7: the latest version is the BASE you read and extend; the
     updated result is SAVED as the next version (rule 1.7) which becomes the new latest.
     You never edit an older version or a dark file. (If the owner instead wants in-place
     edits of the latest file, they must say so — default remains "emit next version".)
1.3  AUTHENTIC SOURCES ONLY. Base every recommendation on official docs / the
     project's own changelog / release notes. No guessing, no folk knowledge.
     Prefer, in order: official docs > official GitHub repo/release notes >
     PyPI/Conda release history > authoritative first-party blog. Record the
     exact source URL(s) with each topic's notes.
1.4  PYTHON 3.12+ COMPATIBILITY. All Python guidance must be valid for CPython
     3.12 or later (3.12 / 3.13 / 3.14). Flag anything deprecated/removed in
     3.12+ and anything requiring a newer minimum. Note library min-Python too.
1.5  CURRENT LIBRARY VERSIONS. For each library, confirm the current stable
     release (as of the session date) and note the version the sheet should
     target. Record "verified against <lib> <version>, <date>".
1.6  DESIGN SYSTEM IS ALREADY STANDARDIZED — do NOT restyle. Content only.
     (Canonical tokens: --ink:#1a1d24 / --paper:#fbfaf8 / Inter + JetBrains Mono.
     See memory note "cheatsheet-design-system".)

1.7  OUTPUT VERSIONING — *** NEVER OVERWRITE THE CURRENT LATEST FILE ***
     DEFAULT IS v0. A file with NO explicit version suffix is version 0. The edit phase
     saves the regenerated cheat-sheet as the NEXT integer version; the current latest is
     left untouched as the previous version.
       - no suffix (= v0)   -> _v1   e.g. matplotlib_cheatsheet_v0.html    -> matplotlib_cheatsheet_v1.html
       - _v0 is the latest  -> _v1   e.g. postgresql_cheatsheet_v0.html -> postgresql_cheatsheet_v1.html
       - _vN is the latest  -> _v(N+1)  e.g. pandas_cheatsheet_v1.html   -> pandas_cheatsheet_v2.html
                                        e.g. python314_cheatsheet_v4.html -> python314_cheatsheet_v5.html
     Pick N from the HIGHEST existing version for the topic (no-suffix counts as 0), then
     write N+1. The new file becomes the canonical latest; update the CURRENT FILE MAP
     (section 4) to point to it.
     SEPARATOR/STYLE: the repo now uses underscores consistently (…_cheatsheet_vN.html;
     Postgres uses …_cheat_sheet[…]_vN.html). Preserve the topic's existing base spelling
     exactly and append _v(N+1). Never invent hyphens.
     *** IMPORTANT (2026-08-23 repo re-version): the repo was renamed to this v0-based
     scheme AFTER the P1/P2 notes were written, so the filenames quoted inside older
     per-topic notes (section 6) may be pre-reorg. The AUTHORITATIVE current filename per
     topic + its next-output name is the CURRENT FILE MAP in section 4. Always resolve
     filenames from section 4, not from the prose in section 6.

1.8  AUTHENTICITY IS NON-NEGOTIABLE (validation gate before build).
     Every planned ADD / EXTEND / UPDATE must be TRUE against the library's official source
     at build time — no folklore, no half-remembered APIs, no version guesses. Rules:
       - Each claim must trace to an official doc / release note / changelog / repo. Cite it.
       - VERSION-ATTRIBUTE claims precisely: state the EXACT version a feature landed in, and
         confirm it applies to the sheet's TARGET (latest) version — not a beta/next release.
         (Real example caught 2026-08-23: the "greenlet no longer installs by default" change is
         SQLAlchemy 2.1, NOT the 2.0.x the sheet targets — see VALIDATION LOG.)
       - Confidence tags on every planned change:
           [CONFIRMED]  = validated against an official source this pass.
           [VERIFY]     = plausible but NOT yet confirmed; MUST be checked at build time.
         Do not ship a [VERIFY] item as fact — confirm or drop it first.
       - Prefer showing the exact current stable version; if unsure, mark [VERIFY], never guess.
       - Deprecations/removals: verify the feature is actually gone (AttributeError-level), not
         merely deprecated, before telling users to stop using it.
     The VALIDATION LOG (section 8) records what was checked and what was corrected.

1.9  TASK LIFECYCLE — DONE = MOVED TO CHANGELOG + REMOVED FROM PENDING.
     When a task is completed IN ITS ENTIRETY (its full scope finished & validated — not
     partially, not merely planned), do BOTH of the following in the same pass:
       (a) RECORD it in the CHANGELOG — now the sibling file CHANGELOG.txt (section 7 is a stub pointer) —
           as COMPLETE, date + what actually shipped;
       (b) REMOVE it from wherever it lived as a pending/active item, so the pending sections
           stay a true list of only OUTSTANDING work. That means:
             - section 5 backlog: delete the finished topic's line (it now lives in the changelog);
             - section 10 new-build backlog: delete the finished [ ] line (and its bundle notes);
             - section 9 active-build spec: once built & validated, remove/retire the spec block;
             - any note whose work is fully delivered.
     Partial progress is NOT moved — leave it in place and just update its marker/status; move it
     only when the WHOLE scope is done. When in doubt about "entirety of scope", it is not done.
     (Historical context that is still useful — e.g. per-topic audit notes in section 6, the
     validation log — may be kept even after the related build ships; this rule is about not
     leaving COMPLETED tasks sitting in the PENDING/BACKLOG lists.)

1.10 PACKAGE-FAMILY GROUPING (group-wise categorizable packages).
     When several related packages form an ECOSYSTEM/FAMILY — e.g. Flask extensions, the
     HuggingFace stack, the Jupyter stack, CLI utilities, DB drivers, a plotting family —
     deliver them as ONE dedicated GROUPED cheat-sheet, SORTED by popularity/importance and
     split into TIERS, rather than many tiny sheets. List ALL tiers as pending items; the OWNER
     chooses which tier(s) to build WHEN PROMPTED at build time (sensible default first pass =
     the top 1-2 tiers). Always flag deprecated members with their maintained replacement, and
     validate each member's version/maintenance at build (rule 1.8). Existing §10 bundles
     (jupyter, python_cli_utils, python_automation, the HF fold-ins) already follow this — apply
     the same behavior to any new family. On completion, rule 1.9 applies (move to changelog,
     remove from pending) so a fresh chat/handoff sees only outstanding work.

2. RESEARCH PROTOCOL (per topic)
--------------------------------------------------------------------------------
STEP 1  Identify the canonical file (section 4) and read/extract its current
        coverage: card/section titles + the specific APIs, commands, flags,
        classes and functions it already lists. (Use grep to pull code tokens;
        don't eyeball the whole file.)
STEP 2  Pull the library's current stable version + release notes / "what's new"
        and its official API reference. WebSearch then WebFetch the official
        pages. Note new/renamed/removed APIs since the sheet was written.
STEP 3  Diff coverage vs. reality. Produce three lists:
          ADD     — genuinely missing but important APIs/idioms/sections.
          EXTEND  — present but thin/incomplete (missing key flags/options).
          UPDATE  — outdated, deprecated, renamed, or Python-3.12+ incompatible.
STEP 4  Note authenticity checkpoints: exact version verified + source URLs.
STEP 5  Write the note block (format in section 3) into section 6, then flip the
        topic's status in section 5 BACKLOG and append a line to CHANGELOG.txt (section 7 is a stub pointer).

DO NOT edit the .html files in this phase. This phase only PRODUCES NOTES. The
actual HTML edits are a later phase driven by these notes (unless the owner says
otherwise).
